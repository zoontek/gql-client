# Caching [How the normalized cache stores and reads back query results.]

`Client` keeps every response in a single normalized cache, shared by all queries. This is what lets `useQuery` read a result instantly when another query already fetched the same data, and what makes a mutation's effect show up everywhere the affected object is rendered.

## How objects are identified

The client adds `__typename` to every selection automatically, so the cache always knows what kind of object it's looking at. An object that also has a string `id` field is stored once, under a `Typename<id>` key, and that single stored copy is what every query reads from. Update the object anywhere and every query showing it picks up the change.

An object without an `id` (or without `__typename`, which shouldn't happen) is stored inline instead, scoped to whichever cached parent holds it.

This is why you should query `id` on any object type that has one, even if your component doesn't use it directly.

## How fields are cached

A field is stored under its closest `id`-keyed ancestor, or under the query/mutation root if there's no such ancestor above it. A field called with arguments, like `characterConnection(first: 5)`, is cached per set of arguments, so querying it again with different arguments doesn't overwrite what's already cached.

## Cache reads are all-or-nothing

Reading a query from the cache only succeeds if every field it asks for has already been cached. There's no partial resolution: a single missing field means the whole query is treated as a cache miss and goes to the network.

## Interfaces and unions

Spreading a fragment on an interface or union, like `... on Node { id }`, requires knowing which concrete types implement it. That mapping isn't in the query document, which is why `Client` needs a `schemaConfig`, generated once from your schema with [`gql-schema-config`](/#2-generate-the-schema-config).
